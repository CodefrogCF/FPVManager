# Drone profiles and parameter provenance

The navigation drawer opens Drone profiles independently of renderer readiness.
Profiles support local creation, listing, details, editing and confirmed deletion.
Small screens put map commands in a separate menu; wide screens retain the map
toolbar. Existing spots remain accessible from the drawer and wide toolbar.

## Recorded data

Name and drone type are required (1–120 trimmed characters). Type is free text,
so existing/custom airframes remain editable. Optional text describes frame/build
configuration, propellers, motors, ESC, measurement context and general notes.
Component descriptions allow 120 characters; configuration and measurement
context allow 4,000. The context can record payload, battery voltage, conditions,
the measurement method or the basis of an estimate.

| Group | Numeric parameters | Units |
|---|---|---|
| Airframe | Takeoff weight; length, width, height | g; mm |
| Propellers | Diameter; pitch; propeller count | in; in; whole count |
| Propulsion | Motor count; motor KV | whole count; rpm/V |
| Power & performance | Maximum speed; cruise speed; maximum climb rate | m/s |
| Power & performance | Hover, cruise and maximum power | W |
| Power & performance | Reference voltage | V |

All numeric parameters are optional. Empty means unknown, not zero. Entered
values must be finite and positive; component counts must be whole numbers
representable consistently on Web and native targets. The editor accepts a
decimal point or decimal comma. No physical parameter is prefilled from the
drone type, and no relationship between measurements taken under different
conditions is assumed.

Each number has its own source: **Measured**, **Estimated** or **Source not
specified**. These are user-supplied classifications, not independent verification
of measurements. Details show the source beside each recorded value in text and
color. General profile lists show name/type rather than unlabeled numeric values.
Editing numeric input resets its old source to unspecified; changing only text
preserves sources. A user can select a source after entering the new value.

This feature records inputs for future flight models. It does not calculate
range, endurance, energy consumption or flight suitability from them. Battery
profiles and radio profiles remain separate feature work (#14/#15).

## Persistence and compatibility

Schema v5 adds nullable technical/component fields to `drones`, plus the
`drone_parameter_sources` table keyed by drone ID and stable parameter key.
Numeric values have one canonical location in the drone record; sources refer
to those fields. Source rows cascade when their drone is deleted. Flight plans
and waypoints survive drone deletion, with the drone assignment set to null.

`DroneProfile` wraps a generated `Drone` plus an immutable typed measurement map.
`getProfile` and `watchProfile` read fields and sources through a single join so
observers receive coherent committed snapshots. Unknown source identifiers,
orphaned source metadata and invalid stored numbers raise `FormatException`.

`createProfile`/`updateProfile` commit the complete profile and sources together.
An update replaces all profile fields and clears omitted optional values.
Failures roll back both values and provenance. Failed editor saves retain the
draft and report an error above the scrollable fields. Cancel does not write.

The existing basic `createDrone`/`updateDrone` API remains available. Basic updates
preserve advanced fields; changed weight/speed values lose their previous source
instead of inheriting an old measured/estimated assertion. Unchanged values keep
their source. As before, omitted basic optional values are cleared.

Migrations from v1, v2, v3 and v4 preserve existing records and references. Legacy
weight/speed have unspecified provenance; migration invents neither measurements
nor estimates. Missing advanced values remain null. Historical schema snapshots
and generated fixtures are retained, with new v5 fixtures generated by Drift.

- The full Flutter suite passed all 161 tests. Thirty focused repository,
  migration, editor, navigation and map-selection tests also passed. After
  strengthening the rollback assertion to check both the original number and
  its measured source, all eight profile repository tests passed again.
- Analysis, formatting, pinned Cesium assets, seven JavaScript bridge tests,
  CI configuration and documentation link checks passed. Dependencies and the
  historical schema definitions/fixtures were preserved.
- Web release and Android ARM64 debug APK built successfully. Packaged renderer
  assets matched their hashes and sources; APK ZIP integrity passed. Its kernel
  contains the current profile UI, provenance model and storage code. The APK
  was not installed on a physical device during this validation.
- In the actual Web release, the drawer opened drone profiles, two independent
  synthetic profiles were created, and technical parameters and mixed sources
  were saved. Editing a measured weight reset its source to unspecified;
  explicitly selecting Measured saved the new value and source together.
  Both profiles, component descriptions, numeric values, source labels and
  measurement context remained available after a complete page reload.
- A 360×640 widget test with a 260-pixel keyboard inset reached the final
  parameter/source fields and Save without layout errors. This is automated
  layout coverage; physical Android UI/keyboard acceptance remains a device check.
